# План до enterprise-пилота

Этот документ описывает только оставшуюся работу. История M0–M6 и детали старого процесса переноса кода удалены: они не помогают оценить состояние продукта.

## Текущее состояние

M0–M6 и программная часть M7 находятся в `main`. Provider, model patch workflow, benchmark harness и fake-HTTP integration покрыты кодом и CI. M7 не завершён: настоящая модель, embeddings, offline, GPU и качество не проверены. Статусы ниже относятся к коду и известным результатам CI, а не к фактической production-готовности.

## Этап 1 — Закрыть hardware/model gate

- На целевом ПК поднять локальный inference server и проверить, что endpoint привязан только к доверенному интерфейсу.
- Запустить выбранную quantized coding model: сначала подходящий вариант 7B, затем сравнить с 14B, только если укладывается в VRAM и приемлем по скорости.
- Подключить локальную embedding model и переиндексировать синтетические данные. Измерить retrieval до подбора reranker.
- Выполнить coding tasks с настоящей моделью: первая попытка и максимум два repair.
- Предварительно загрузить все модели и container images, отключить интернет и повторить запуск.
- Записать фактические версии, параметры, VRAM/RAM, latency, tokens/sec, task duration и ошибки.

**Выход этапа:** воспроизводимый локальный прогон с evidence, что система не обращается к внешним AI-сервисам. Нельзя заранее обещать, что конкретные модели поместятся на GPU или обеспечат требуемое качество.

## Этап 2 — Сделать benchmark пригодным для решения

- Расширить текущие три синтетические задачи до разнообразного набора coding задач.
- Для каждой задачи зафиксировать base commit и независимые acceptance tests, недоступные модели.
- Сравнить Base, RAG и RAG + test loop на одной версии модели и данных.
- Оценивать не только прохождение тестов, но и patch safety, изменения тестов, human acceptance, качество citations и отказы.
- До прогона определить пороги успеха и провала.

**Выход этапа:** воспроизводимый отчёт, который позволяет объяснить, где система помогает, а где ошибается. Текущие три задачи остаются smoke-level проверкой.

## Этап 3 — Приёмка 2–3 тестировщиками

- Зафиксировать tag и окружение; выдать отдельные учётные записи.
- Дать одинаковые сценарии без подсказок автора.
- Проверить setup, разрешённые/запрещённые проекты, citations, отказ, code search, coding loop и review.
- Записать evidence, severity и частоту каждого дефекта.
- Исправить блокирующие находки и повторить benchmark.

**Выход этапа:** документированное решение `go`, `conditional-go` или `no-go` только для ограниченного пилота.

## Этап 4 — Подготовить изолированный enterprise-пилот

До допуска внутренних проектных репозиториев нужен отдельный architecture/security review и как минимум:

- SSO/OIDC, lifecycle и отзыв пользовательских credentials;
- per-project/repository authorization, проверенная на реальных ACL-сценариях;
- внутренний registry моделей/образов, закреплённые версии и проверка hashes;
- отдельные sandbox workers с более сильной изоляцией, чем Docker POC;
- quotas и очереди для inference и coding jobs;
- нагрузочные, отказные, backup/restore и incident-response проверки;
- политики хранения кода, audit, prompts, logs и сроков удаления;
- protected branches, code owners, обязательные CI и человеческий merge.

Не рассчитывать ёмкость под 100 разработчиков до нагрузочных измерений на целевых моделях и железе.

## Не блокирует первый пилот

Fine-tuning/LoRA не является обязательной задачей. Его стоит рассматривать только после классификации ошибок и доказательства, что конкретную повторяемую проблему нельзя решить retrieval, prompt, policy или обычным исправлением кода. Eval-набор нельзя использовать для обучения.
